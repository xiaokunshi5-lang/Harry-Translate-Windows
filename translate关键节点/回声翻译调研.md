### 3. Echo Translate 端到端运行流水线

```
[1. 音频采集]
   默认: 浏览器原生麦克风 (Chrome Web Speech API, 无 Loopback)
   实验性: Web Audio API (HPF 90Hz -> 2.5kHz Peaking -> Compressor -> 动态增益 -> Limiter)
           -> MediaStreamDestination.track -> SpeechRecognition.start(track) (持续 8s 无声自动回退)
   │
   ▼ onresult 事件 (continuous=true, interimResults=true; onend 650ms 自动重启)
[2. 前端瞬时清洗与分段 (同步执行，单次延迟 < 1ms)]
   cleanSpeech() [剔除 um/uh 等语气词, 4->1 元连续重复词压缩, 近音截断纠正]
   -> fixTerms() [基于 Levenshtein 模糊编辑距离匹配术语表]
   -> mendFragment() [去除悬挂连词/介词后的假句号，下句首字母降小写]
   -> assignPara() [以 6 句/520 字符为软上限，严格在完整句尾切分自然段]
   │
   ├──► [3a. 低延迟翻译队列 (单并发串行，40ms 防抖)]
   │      调度优先级: translateUrgent (纠错重排) > translatePending (定稿整段) > interimPending (尾词快翻)
   │      首选引擎: window.Translator.translate() (Chrome 138+ 端侧本地模型，零 API 费用)
   │      备用引擎: POST /api/translate -> 本地 Ollama (/api/chat, timeout 35s)
   │      质量巡检: untranslatedWords() 检查译文中未译英文词 >= 2 时，标红 suspect=true 并将下一轮纠错提前至 +1.5s
   │
   ├──► [3b. 后台异步语义分析流水线 (500ms Tick 驱动，双节拍调度)]
   │      轻量纠错拍: 有未决断定稿英文时，每 1.5s 启动纯纠错与整段译文对齐 (notes_due=false)
   │      深度分析拍: 每 10s/30s 刷新 1-5 级重点 (4-5 级核心常驻，1-3 级归档)；每 40s 刷新教授预测 Q&A
   │      执行机制: POST /api/insights -> 后端起 daemon 线程，MODEL_LOCK Semaphore(1) 限制单并发串行
   │               -> Codex CLI (subprocess.run 外部进程: --ephemeral --sandbox read-only -c model_reasoning_effort=low)
   │               -> Ollama (/api/chat, format="json", temp=0.15)
   │               -> 免模型规则: rulesInsights() 词法模式匹配
   │      后端护栏: plausible_correction() 词距安全阀 (增词 <= max(3, 0.3*len), 禁乱加内容) + 反叙事腔正则剥离
   │      前端消费: 400ms 短轮询 GET /api/jobs/:id -> 乐观锁比对 (若原句已被修改则丢弃，防时序颠倒)
   │
   └──► [4. 本地持久化与会话生命周期]
          2s 防抖触发 saveSession() -> clientSavedAt 单调时间戳校验 (防乱序网络包覆盖恢复草稿)
          -> SAVE_LOCK 互斥锁 -> 写入 .tmp 临时文件 -> os.replace() 原子替换落盘至 ~/Documents/EchoTranslate-Records/
          -> 浏览器端 pagehide / visibilitychange 热备草稿至 localStorage -> 启动 3 小时内自动续接会话
```

## 二、本地三版同传演进深度技术审计（V1 → V2 → V3）

本地三个项目文件夹记录了从“原型演示”到“全功能同传”，再到“工业级旗舰同传”的完整工程演进过程：

### 1. 最初版（V1）：极简双大屏投屏网关
- **位置**：本仓库
- **代码规模**：15 个文件，2,463 行代码。后端单文件 `server.py`（396 行），前端单文件 `index.html`（740 行），无 `.git` 版本库，**0 单元测试**。
- **技术实现**：
  - 音频：`PyAudio` 单流拾音，`CHUNK_SIZE=3200`（对应 **200ms** / 6,400 字节，注：文档注释误写为 100ms），单麦克风拾音，无回环（Loopback），无 AGC，无设备热插拔自愈。
  - 云端：`websocket.WebSocketApp` 维护双连接（`channel_en` 与 `channel_zh`），固定推送阿里云公网 MaaS Qwen 3.8 实时流。双连接无论是否有前端观看，**24/7 全天候推流计费**。
  - 广播：单线程内对 WebSocket 客户端执行**串行阻塞遍历广播**（`timeout=1.0s`），极易发生队头阻塞。
  - 界面：纯浏览器页面（`/`, `/en`, `/zh`, `/split`），黑色背景，高对比度黄白大字，最大保留 100 张卡片，直接写 `innerText`。
  - **严重性能隐患**：前端 WebSocket 每次收到流式增量（Delta）都会立刻触发一次 `fetchStats()` HTTP 请求，产生巨量网络风暴。

### 2. 未改进版（V2）：跨平台透明悬浮窗与词库工作台
- **内部代号**：`v3.8-glossary-bank-smart-quota-workbench`
- **位置**：本地另一独立版本，不含于当前仓库
- **代码规模**：134 个文件，49,072 行。生产 Python 核心（2,775 行），前端 `index.html`（2,941 行）+ `float_ui.html`（1,581 行），`glossary_bank/` 15 个词库包（18,689 行），测试集包含 74 个文件、14,149 行（396 个测试方法）。无 `.git`。
- **相比 V1 的重大技术突破**：
  1. **音频采集质变**：切片粒度由 200ms 收敛至 **50ms**（800 采样点 / 1600 字节）；新增物理麦克风（`worker_a`）与数字回环（`worker_b`）双轨架构；支持设备热切与掉线重连。
  2. **网关性能优化**：广播改为 `asyncio.gather` 并发广播，并设置 `0.25s` 超时硬熔断；引入 `Client-Aware Stream Gating` 客户端感知门控，单通道断开时自动节约 50% 音频上行。
  3. **原生透明 HUD 悬浮窗诞生**：引入 `pywebview 5.0+` + macOS Cocoa 原生深度魔改（`NSPanel` 非激活全屏置顶、`NSWorkspaceActiveSpaceDidChangeNotification` 跨桌面漫游追随、左上角穿透原生拖拽、VisionOS 风格 15% 微透毛玻璃、稳态无频闪排版、68:32 黄金分割双区防挤压视口）。
  4. **构建 P0–P3 四级词库体系与纯 Python AC 自动机**：支持 15 个学科词包、18,449 词，毫秒级 Aho-Corasick 树搜索，`#config-drawer` 抽屉工作台与冲突探针。
- **暴露出的工程技术债务**：
  - **网络推流反向阻塞音频采集**：在 `server.py` 中，`run_audio_sender` 线程函数被架空（直接写为 `pass`），`push_audio()` 居然在 `PyAudio` 的音频回调线程中**同步调用 WebSocket 发送**，使得 Drop-Oldest 环形缓冲队列形同虚设！
  - **4 倍并发连接与重复启动 Bug**：`ChannelSession.start()` 同时无条件启动 Gummy 和 Qwen 两个引擎（单通道 2 连接，双通道共 4 连接）；且 `main()` 与 `lifespan()` 各启动了一次，导致启动时向云端重复注册连接。
  - **Token 计费统计在第 2 句起永久冻结**：底层未向发出的负载中塞入 `usage`，导致累加逻辑失效，`/api/stats` 永远停留在第一句的估算字数。
  - **测试反向污染生产代码（Reward Hacking）**：为了强行通过脆弱的正则断言测试，在 `float_ui.html` 生产代码里写死了 3 层重复 CSS 属性、将顶栏按钮用 `<span>` 伪装以规避“按钮总数 <= 3”的限制、放置了多个 `display:none` 的幽灵 DOM（`#legacy-compat-container`），甚至硬编码了测试专用的字符串比对分支。

### 3. 阿里同声传译（V3 旗舰版）：工业级高压会议同传系统
- **内部代号**：`Release-v4.0.0 Flagship`（Git 仓库：`xiaokunshi5-lang/harry-translate`）
- **位置**：本地另一独立版本，不含于当前仓库
- **代码规模**：生产 Python 8 个文件（7,814 行），前端 `index.html`（3,118 行）+ `float_ui.html`（2,152 行），15 个词库包（18,449 词），测试套件包含 87 个文件、20,336 行（**454** 个单元测试用例）。
- **相比 V2 的硬核优化与修复**：
  1. **音频与协议链路加固**：
     - 增加 **远场自适应 AGC**（4 段分段线性增益 + EMA 平滑 + 峰值硬钳位），弱音最高补偿 3.2 倍；
     - 彻底修复 V2 的推流阻塞，为 Qwen 3.8 设立独立的 Drop-Oldest `_tx_queue(maxsize=64)` 异步发送队列；
     - 接入云端 `server_vad`（静音截断 240ms）+ 本地 `2.4s / 3.8s` 周期性主动 Commit 机制，彻底消除首字延迟积压；
     - 修复 V2 的 4 倍连接 Bug，仅启动当前激活的引擎。
  2. **悬浮提词体验极致打磨**：
     - macOS 端注入 `NSTrackingActiveAlways`，彻底解决未激活窗口鼠标划过顶栏不响应悬停的顽疾，实现 0px 贴顶盲操呼出；
     - 3 档字号阶梯无级缩放（`Cmd/Ctrl+Shift+F`），原生 WebKit DOM 直写（`0.0018ms`），辅以 `300ms` 微停顿智能合并，彻底杜绝跳字闪烁；
     - 双浮窗（`--dual`）对称镜像排版与跨语种纯度锁（`sanitizeTargetForChannel`），杜绝中英回声与语言污染。
  3. **词库逻辑修正**：为 AC 自动机补齐了 **ASCII 字母数字单词边界保护**，防止 `AI` 误伤 `OpenAI` 或 `SAID`；将云端动态同步配额控制在 `<=48` 词高精增量帧内。
- **源码审计发现的现存硬伤（需列入重构清单）**：
  1. **Token 统计仍然停摆**：`engines/qwen_translators.py:1456` 的 `_dispatch_payload` 依然漏传 `usage`，`/api/stats` 仍会在第二句后停止增长。
  2. **空客户端时空转烧费**：`server.py:691-693` 在 `all_connected == 0` 时返回 `True`，服务开启后即便没有打开网页或悬浮窗，依然会源源不断向云端推流计费。
  3. **AC 译文纠偏逻辑在方向上存在结构性错位**：`core/glossary_manager.py:576-584` 在中译英（`channel="en"`）时，竟然把中文键的自动机作用在已经翻译完成的英文 `target_text` 上！导致其根本无法纠正英文译名的偏颇，只能靠云端 48 词配额去碰运气。
  4. **94.5%（17,436 词）为人工合成长词**：`09` 至 `14` 号生僻词包全是由笛卡尔积模板拼凑出的超长复合词（如 `“临床试验三期程序性死亡受体配体1疗效评估标准”`），实战口语几乎不可能逐字命中，反而严重拖慢检索并挤占内存。
  5. **HUD 偏好设置无法跨会话保存**：`float_app.py:216` 采用了 `nonPersistentDataStore()`，导致用户在悬浮窗上调好的字号、配色、透明度，**每次重启程序后全被清空重置**。
  6. **安全漏洞与假功能**：默认 WebSocket 连接关闭了 TLS 证书验证（`ssl.CERT_NONE`）；局域网开共享时写接口毫无鉴权；控制台的“远程开启隐身”按钮调用的接口在后端根本不存在，却依然弹出假的成功提示。

## 四、同传方案与当前项目各自的优势与源码级实证不足

### 1. 您的同传方案（以 V3 旗舰版为代表）

#### 核心优势
1. **真正的专业级同传时延与声学工程**：
   采用 50ms 零拷贝分片、4 段分段式自适应 AGC 增益补偿、双工声卡支持（麦克风 + 软件回环），并为 Qwen 3.8 适配了 `server_vad`（240ms）与端侧 `2.4s/3.8s` 主动 Commit 策略，首字时延（TTFT）压至 380ms 以内，彻底摆脱了 Web Speech API 必须等待句末停顿 2 秒才能定稿的硬伤。
2. **极佳的原生桌面 HUD 悬浮提词体验**：
   借助 `pywebview` 深度绑定 macOS Cocoa 原生 API（`NSPanel`、`NSPopUpMenuWindowLevel`、`CanJoinAllSpaces`），配合 VisionOS 风格的高清微透毛玻璃与稳态排版渲染，在全屏播放 PPT、Keynote 或进行 Zoom 会议时，能无缝浮动在界面最上层，实现 0px 贴顶盲操呼出与单/双屏对称镜像。
3. **高精度术语控制与热词水位管理**：
   自研纯 Python Aho-Corasick 自动机，具备 ASCII 单词边界保护；控制台支持 P0（临时会议词）至 P3 级精细分类管理、增量热词同步（`<=48` 词高精帧）与冲突探针。

#### 源码级实证不足（必须在演进中予以解决）
1. **产品定位严重缺乏“会后资产沉淀”**：
   数据“转瞬即逝”，内存中仅保留 50 张卡片，滚出即物理销毁。没有任何持久化机制、没有草稿恢复、没有字幕或纪要导出能力。
2. **底层 100% 绑定单一商业 API，存在静默烧费风险**：
   强依赖阿里云 DashScope 付费接口，没有本地或免费兜底方案；同时源码中 `is_channel_subscribed` 在全站 0 人连接时依然持续推流，造成严重的空转扣费。
3. **词库与计费逻辑存在逻辑硬伤**：
   - 累加统计 Bug 导致 `/api/stats` 在第 2 句后完全冻结；
   - AC 自动机在翻译纠偏时，把中文词表应用在已经译好的英文上，导致无法利用本地词库纠正英文术语的翻译偏差；
   - 18,449 词中 94.5% 为低频模板合成词，实用价值极低。
4. **前端单文件膨胀与测试反向污染**：
   前端巨石文件达 5,270 行；为了迎合旧测试门禁，在生产代码中残留了大量幽灵 DOM、伪装 `<span>` 控件与硬编码测试分支。

### 2. Echo Translate（回声翻译）方案

#### 核心优势
1. **极致的零边际成本与轻量化部署**：
   基于 Python 3.10+ 标准库实现全套后端（无 `pip install` 门槛），直接白嫖 Chrome 138+ 端侧内置大模型 `window.Translator`，高阶语义分析消耗个人已有的 ChatGPT/Codex 订阅或本地 Ollama，彻底避开了商业 API Key 的调用计费。
2. **教科书级别的防幻觉异步纠错流水线**：
   - 翻译前瞬时清洗（`cleanSpeech` / `fixTerms` / `mendFragment`）能在毫秒级消解口误与连音；
   - 后端大模型分析配备了严格的 `plausible_correction()` 词距与长度硬护栏，坚决防止大模型自由发挥篡改原意；
   - 正则剔除叙事腔 + 前端乐观锁（比对原句 Hash）防止乱序覆盖；
   - 当检测到未译英文词残留时，自动将加急纠错节拍提前至 1.5s。
3. **稳健严密的本地数据持久化与安全防护**：
   - 2 秒防抖落盘 + `SAVE_LOCK` 线程锁 + `clientSavedAt` 单调时间戳校验（彻底避免乱序网络请求覆盖恢复的草稿）+ `.tmp` 临时文件原子替换；
   - 页面切入后台时热备至 `localStorage`，支持 3 小时内意外中断一键续课；
   - 强制绑定 `127.0.0.1`，自带 DNS Rebinding 与 Origin 校验防 CSRF，Codex 调用强制包裹 `--ephemeral --sandbox read-only` 只读沙箱。

#### 核心短板与局限
1. **ASR 强绑定浏览器 Web Speech API，无法胜任会议与网课**：
   完全不支持系统声音内录（Loopback），甚至连麦克风硬件选择器都没有。在视频会议或网课场景下，只能靠扬声器外放回录，噪音极大；且在线识别受制于 Google 语音网络通道，存在不可调控的 2 秒停顿硬延迟。
2. **缺乏置顶透明悬浮形态（Floating HUD）**：
   仅提供全屏独占的 3 列 4 面板浏览器界面，无法悬浮在课件、文献或视频上方，遮挡严重。
3. **课件解析与实时识别存在严重功能脱节**：
   虽然能原生解析 `.docx` 和 `.pptx`，但提取出的内容仅仅作为后续 LLM 的上下文背景，**根本没有自动生成专有名词词表，更没有打通实时 ASR 偏置**，宣传与实现严重不符。

## 六、可落地的整合优化演进方案（P0 → P3 路线图）

> **基座决策结论**：**必须以 `阿里同声传译`（V3 旗舰版）作为底层工程基座**，通过在其之上增量嫁接 Echo Translate 的优秀机制进行升级。
>
> **理由**：若以 Echo Translate 为基座，需要彻底推翻重写其音频采集底层、引入 WebSocket 网关、重造原生非激活置顶悬浮窗，改造成本高达 6–8 人周且风险极高；而在 V3 基座上，引入文件原子持久化、文档解析、异步分析队列与安全护栏，均属于模块化扩展，在**零破坏当前 380ms 极速主同传时延**的前提下即可完美实现。

### 阶段 P0：核心缺陷修复、安全加固与生产代码清淤（最高优先级）
- **止血静默扣费与计费冻结**：
  - 在 `engines/qwen_translators.py:1456` 中正确补齐增量 `usage` 载荷，使 `server.py` 与 `/api/stats` 恢复真实 Token 统计；
  - 修复 `server.py:691`，当所有客户端断开时（`all_connected == 0`）立即挂起向云端的音频推流，防止服务后台空转扣费。
- **纠正 AC 自动机译文纠偏方向**：
  - 重构 `core/glossary_manager.py:576`，将词表明确区分为 `asr_fixes`（纠正源语口误）、`terms_trans`（辅助翻译）与新增的 `target_fixes`（专门纠正英文/中文译文中的偏颇词汇）。
- **加固网络与系统安全**：
  - 移除 `qwen_translators.py` 与 `switch_key.py` 中的 `ssl.CERT_NONE`，恢复标准 TLS 证书校验；
  - 引入 Echo Translate 的 Host/Origin 校验，当开启局域网投屏（`HOST=0.0.0.0`）时，对修改声卡、删除词库、更改 API Key 等写接口强制启用本机 Token 鉴权。
- **修复 HUD 偏好丢失与假功能**：
  - 移除 `float_app.py:216` 中的 `nonPersistentDataStore()`，换用持久化配置存取，使悬浮窗字号、透明度与配色重启后依然保留；
  - 在 `server.py` 中补全 `/api/hud/stealth` 真实端点，消除控制台虚假成功 Toast；
  - 清理 `float_ui.html` 中残留的 3 层重复 CSS、`#legacy-compat-container` 幽灵 DOM 与伪装 `<span>` 按钮。

### 阶段 P1：会话生命周期闭环——原子持久化与课件直通热词（吸收 Echo 精华）
- **构建高可靠会话存储器（`core/session_store.py`）**：

### 阶段 P2：异步语义分析与知识沉淀旁路（零时延侵入）
- **构建独立后台异步推理服务（`core/insight_worker.py`）**：
  - 独立于主同传音频流（完全不影响 `<380ms` 的极速同传主路径），支持通过任务队列异步处理定稿段落；
  - **四级推理驱动灵活切换**：
    1. DashScope 通义文本大模型（复用已有 Key）；
    2. 本地 Ollama（免费开源模型，如 `qwen2.5:3b`）；
    3. Codex CLI（消耗用户已有的 ChatGPT 网页版订阅，强制使用 `--sandbox read-only` 沙箱）；
    4. 纯启发式规则引擎（零模型环境门槛）。
  - **移植防幻觉与质量监控机制**：
    - 引入 `plausible_correction()` 算法，强制校验大模型纠偏词距，杜绝自由发挥与幻觉生成；
    - 引入 `_EN_NARRATION`/`_ZH_NARRATION` 正则剥离叙事腔，配合前端乐观锁防止乱序覆盖；
    - 引入 `untranslatedWords()` 巡检机制，当发现译文中存在大量未译单词时自动加急下一轮纠错；
    - 异步生成分级知识重点（4–5 级置顶，1–3 级归档）与预测 Q&A。
- **词库瘦身与有效性治理**：
  - 默认停用并剥离 `09` 至 `14` 号占总量 94.5% 的合成长词包，大幅降低内存开销；
  - 为 ASR 修正引入短距离 Levenshtein 模糊纠错。
